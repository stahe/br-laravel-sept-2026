    9. Arquitetura em camadas e acesso a dados

    Os exemplos anteriores armazenavam seus dados na memória ou no cache. Uma aplicação real os armazena em um banco de dados e é organizada em camadas (veja o diagrama na introdução):

    • a camada web (controllers, views): lê a requisição, chama a camada de negócio, seleciona a view;
    • a camada de negócio: regras de negócio;
    • a camada DAO (*Data Access Object*): consultas ao banco de dados.

    Cada camada conhece apenas a camada imediatamente abaixo dela, e o mínimo possível de detalhes sobre ela: a camada web desconhece a camada SQL, e a camada de negócio desconhece a camada HTML. Essa separação torna cada camada mais fácil de entender, testar e evoluir. O exemplo 28 aplica isso ao gerenciamento de uma lista de pessoas: é, em menor escala, o gerenciamento de médicos e clientes do estudo de caso.

    No [PHP], o acesso ao banco de dados é organizado em várias camadas:

    • a extensão PDO (*PHP Data Objects*) do [PHP] define uma interface comum a todos os módulos de SGBD: abrir uma conexão, executar um comando SQL e ler linhas. Cada SGBD tem seu próprio driver: [pdo_mysql] para o [MySQL] (e o [MariaDB]), incluído no [PHP];
    • o query builder (*query builder*) do [Laravel] (facade [DB]) constrói os comandos SQL a partir de chamadas de métodos ([where], [orderBy]...), independentemente do SGBD, e gerencia conexões e transações;
    • o Eloquent, o ORM (*Object-Relational Mapper*) do [Laravel], mapeia classes (models, conforme definidos pelo [Eloquent]) para tabelas do banco de dados e transforma as linhas recuperadas em objetos. Ele segue o chamado modelo *Active Record*: cada objeto sabe como se ler e se salvar ([Person::find(1)], [$person->save()]).

    Isso equivale ao [JDBC], [JPA], e ao [Hibernate] no [Java], ao [Entity Framework Core] no [C#], ou ao [SQLAlchemy] no [Python]. Observe uma consequência do funcionamento do [PHP]: como nada sobrevive à requisição, cada requisição abre sua própria conexão com o banco de dados (na primeira requisição SQL) e a fecha ao terminar. Não há pool de conexões como no [Java] ou no [Python]; abrir uma conexão com o [MySQL] na mesma máquina leva apenas uma fração de milissegundo.

    Este exemplo exige que um servidor [MySQL] (ou [MariaDB]) esteja em execução: o apêndice explica como instalar um usando o [Laragon].

    -- banco de dados do exemplo 28: uma única tabela, [persons]
-- o script é escrito em UTF-8
SET NAMES utf8mb4;
DROP DATABASE IF EXISTS dbpersons;
CREATE DATABASE dbpersons CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
USE dbpersons;

CREATE TABLE persons (
  id INT NOT NULL AUTO_INCREMENT,
  -- a versão da linha, incrementada a cada modificação (veja camada DAO)
  version INT NOT NULL DEFAULT 0,
  first_name VARCHAR(30) NOT NULL,
  last_name VARCHAR(30) NOT NULL,
  age INT NOT NULL,
  PRIMARY KEY (id),
  -- duas pessoas não podem ter o mesmo nome e sobrenome
  CONSTRAINT unq_persons_first_name_last_name UNIQUE (first_name, last_name)
) ENGINE = InnoDB;

INSERT INTO persons (first_name, last_name, age) VALUES
  ('Marie', 'Pélissier', 42),
  ('Jacques', 'Bromard', 35),
  ('Philippe', 'Jandot', 58);
    • Linha 3: o script é escrito em [UTF-8]; isso é informado ao servidor para que os acentos dos dados ([Pélissier]) permaneçam intactos;
    • linha 5: o conjunto de caracteres [utf8mb4] aceita todos os caracteres (acentos, emojis etc.). A collation [utf8mb4_unicode_ci] compara strings sem distinguir letras maiúsculas ou acentos: para o [MySQL], [pelissier] e [Pélissier] são iguais;
    • linha 11: um número de versão, incrementado cada vez que a linha é modificada (veja “bloqueio otimista”, abaixo);
    • linha 17: uma restrição de unicidade nomeada: o banco de dados não permite duas pessoas com o mesmo nome e sobrenome. O nome será usado para identificar o erro.

    O [Laravel] também pode criar as tabelas por conta própria, usando migrações: classes [PHP] que descrevem, passo a passo, a criação e as modificações de cada tabela (comando [php artisan migrate]). Mantemos um script SQL, comum a todas as versões do estudo de caso, que mostra exatamente o que o banco de dados contém.

// bootstrap/app.php: a aplicação do exemplo 28

use Illuminate\Database\Events\QueryExecuted;
use Illuminate\Database\Events\TransactionBeginning;
use Illuminate\Database\Events\TransactionCommitted;
use Illuminate\Database\Events\TransactionRolledBack;
use Illuminate\Foundation\Application;
use Illuminate\Support\Facades\DB;
use Illuminate\Support\Facades\Event;

(require __DIR__.'/../../vendor/autoload.php')->addPsr4('App\\', __DIR__.'/../app/');

return Application::configure(basePath: dirname(__DIR__))
    ->withRouting(
        web: __DIR__.'/../routes/web.php',
        // a rota que serve o Bootstrap (veja o exemplo 15)
        then: fn () => require __DIR__.'/../../common/bootstrap.php')
    ->withMiddleware()
    ->withExceptions()
    ->booted(function () {
        // DB_LOG=true (arquivo .env): cada comando SQL, e cada etapa de uma
        // transação, é exibido no console do servidor
        if (env('DB_LOG')) {
            DB::listen(fn (QueryExecuted $q) =>
                error_log($q->sql.' '.json_encode($q->bindings, JSON_UNESCAPED_UNICODE)));
            Event::listen(TransactionBeginning::class, fn () => error_log('BEGIN'));
            Event::listen(TransactionCommitted::class, fn () => error_log('COMMIT'));
            Event::listen(TransactionRolledBack::class, fn () => error_log('ROLLBACK'));
        }
    })
    ->create();
    • Linhas 24–30: se [DB_LOG] for igual a [true], cada comando SQL é exibido no console. [DB::listen] registra uma função chamada após cada comando SQL, com um objeto [QueryExecuted] (o texto do comando, seus parâmetros e sua duração). [Event::listen] registra uma função chamada a cada evento de um determinado tipo: [Laravel] sinaliza assim, entre outras coisas, o início, a confirmação e o cancelamento de transações. Os eventos são outra maneira — junto com os middlewares — de intervir no funcionamento do framework. (Lemos [env] diretamente, por brevidade; uma aplicação típica usaria um arquivo de configuração; veja o exemplo 25.)

    Não há mais nada a configurar: as classes das três camadas são criadas pelo contêiner do [Laravel], que injeta a camada inferior em cada uma (o controller recebe a camada de negócio, e a camada de negócio recebe a camada DAO).

    <?php
// app/Models/Person.php: uma linha da tabela [persons], um "model" do Eloquent

namespace App\Models;

use Illuminate\Database\Eloquent\Model;

// Model: a classe pai das entidades do Eloquent, o ORM do Laravel. As colunas
// da tabela se tornam, sem declarar nada, propriedades do objeto ($p->last_name)
class Person extends Model
{
    // o nome da tabela (o Eloquent o deduziria do nome da classe: people)
    protected $table = 'persons';

    // a tabela não possui as colunas created_at e updated_at que o Eloquent mantém por padrão
    public $timestamps = false;

    // as colunas que podem ser preenchidas em massa: new Person([...]), update([...])
    protected $fillable = ['first_name', 'last_name', 'age'];

    // as conversões de tipo, coluna por coluna
    protected function casts(): array
    {
        return ['age' => 'integer', 'version' => 'integer'];
    }
}
    • Linha 10: um modelo [Eloquent] herda da classe [Model]. As colunas da tabela não são declaradas: o [Eloquent] lê a linha, e cada coluna se torna uma propriedade do objeto ([$p->last_name], [$p->version]). A chave primária é, por padrão, a coluna [id], gerada pelo banco de dados ([AUTO_INCREMENT]);
    • linha 13: a tabela associada à classe. O [Eloquent] a derivaria sozinho a partir do nome da classe, colocando-o no plural (em inglês);
    • linha 16: por padrão, o [Eloquent] mantém duas colunas, [created_at] e [updated_at], que ele presume estarem presentes em todas as tabelas. A nossa não as tem;
    • linha 19: as colunas que podem ser preenchidas “em massa” a partir de um array ([Person::create([...])]). Trata-se de uma precaução: um array vindo de um formulário poderia conter outras colunas ([version], [id]...), que não queremos que sejam preenchidas dessa forma;
    • Linhas 22–25: conversões de tipo: o driver converte certas colunas numéricas em strings; [casts] garante que sejam inteiros. Há conversões para booleanos, datas (objetos [Carbon]), decimais, arrays (uma coluna JSON)...

    <?php
// app/Dao/PersonsDao.php: a camada DAO, consultas, nenhuma regra de negócio

namespace App\Dao;

use App\Business\PersonData;
use App\Models\Person;
use Illuminate\Database\Eloquent\Collection;
use Illuminate\Support\Facades\DB;

class PersonsDao
{
    // SELECT * FROM persons ORDER BY last_name, first_name
    public function list(): Collection
    {
        return Person::orderBy('last_name')->orderBy('first_name')->get();
    }

    // SELECT * FROM persons WHERE id = ? LIMIT 1; null se a pessoa não existir
    public function read(int $id): ?Person
    {
        return Person::find($id);
    }

    // uma pessoa com os mesmos nome e sobrenome, diferente de [$exceptId]:
    // SELECT * FROM persons WHERE first_name = ? AND last_name = ? AND id <> ? LIMIT 1
    public function namesake(string $firstName, string $lastName, int $exceptId = 0): ?Person
    {
        return Person::where('first_name', $firstName)->where('last_name', $lastName)
            ->where('id', '<>', $exceptId)->first();
    }

    // INSERT INTO persons (first_name, last_name, age) VALUES (?, ?, ?); o banco de dados gera
    // o id, que o Eloquent armazena no objeto
    public function add(PersonData $data): Person
    {
        return Person::create(['first_name' => $data->firstName, 'last_name' => $data->lastName,
            'age' => $data->age]);
    }

    // o BLOQUEIO OTIMISTA: UPDATE ... SET ..., version = version + 1
    // WHERE id = ? AND version = ?; retorna o número de linhas modificadas (0: a
    // linha foi modificada, ou excluída, desde que foi lida)
    public function edit(int $id, int $version, PersonData $data): int
    {
        return Person::where('id', $id)->where('version', $version)->update([
            'first_name' => $data->firstName, 'last_name' => $data->lastName, 'age' => $data->age,
            // DB::raw: uma expressão SQL, escrita como está no comando SQL
            'version' => DB::raw('version + 1'),
        ]);
    }

    // DELETE FROM persons WHERE id = ?
    public function delete(int $id): void
    {
        Person::whereKey($id)->delete();
    }
}

    A camada DAO contém apenas consultas, sem nenhuma lógica de negócio. Cada método usa a conexão da requisição atual e participa da transação aberta, se houver, iniciada pela camada de negócio.

    • Linhas 14–17: [Person::orderBy(...)] inicia uma consulta na tabela de pessoas; os métodos são encadeados ([orderBy] adiciona uma ordenação) e [get()] executa a consulta. O resultado é uma coleção [Eloquent] (exemplo 03) de objetos [Person];
    • linhas 20–23: [find]: recuperação pela chave primária, ou [null];
    • linhas 27–31: [where(column, value)] adiciona uma condição de igualdade; [where(column, operator, value)] adiciona qualquer condição. Os valores são passados ao banco de dados como parâmetros do comando SQL (os marcadores [?] do comando) e nunca são copiados para o seu texto, o que torna a injeção de SQL impossível. [first()] retorna a primeira linha ([LIMIT 1]) ou [null];
    • linhas 35–39: [Person::create] cria o objeto a partir de um array (dentro do escopo de [$fillable]) e o insere no banco de dados; o [Eloquent] armazena no objeto o ID gerado pelo banco de dados;
    • linhas 44–51: a atualização, com um bloqueio otimista. O comando [UPDATE] tem duas condições: o ID da pessoa e a versão lida quando o formulário foi exibido. Ele incrementa a versão em 1: [DB::raw] insere uma expressão SQL como está ([version + 1]), em vez de um valor. Se outra requisição tiver modificado a linha nesse meio-tempo, sua versão mudou, e o [UPDATE] não modifica nenhuma linha: [update] retorna o número de linhas modificadas, que neste caso é 0. Esse é o princípio do bloqueio otimista: nada é bloqueado, mas as modificações concorrentes são detectadas. (O [Eloquent] não gerencia um número de versão por conta própria, ao contrário do [Hibernate] ou do [SQLAlchemy]: a condição é escrita à mão.);
    • linhas 54–57: um [DELETE], construído da mesma forma ([whereKey]: uma condição sobre a chave primária).

    <?php
// app/Business/PersonsBusiness.php: a camada de NEGÓCIO, as regras de negócio, e apenas
// elas. Cada operação que escreve é uma TRANSAÇÃO: confirmada (COMMIT) se a
// função terminar normalmente, cancelada (ROLLBACK) se uma exceção sair dela

namespace App\Business;

use App\Dao\PersonsDao;
use App\Models\Person;
use Exception;
use Illuminate\Database\Eloquent\Collection;
use Illuminate\Database\QueryException;
use Illuminate\Support\Facades\DB;

class PersonsBusiness
{
    private const NAMESAKE = 'A person already has these first and last names.';

    private const MODIFIED = 'This record has been modified meanwhile: reload it.';

    private const UNKNOWN = 'This person does not exist (anymore).';

    public function __construct(private PersonsDao $dao)
    {
    }

    public function list(): Collection
    {
        return $this->dao->list();
    }

    public function read(int $id): Person
    {
        return $this->dao->read($id) ?? throw new BusinessException(self::UNKNOWN);
    }

    public function add(PersonData $data): Person
    {
        try {
            // DB::transaction: a função é executada em uma transação
            return DB::transaction(function () use ($data) {
                // regra 1: não há duas pessoas com o mesmo nome e sobrenome
                if ($this->dao->namesake($data->firstName, $data->lastName)) {
                    throw new BusinessException(self::NAMESAKE);
                }
                return $this->dao->add($data);
            });
        } catch (QueryException $e) {
            throw self::translate($e);
        }
    }

    public function edit(int $id, int $version, PersonData $data): Person
    {
        try {
            return DB::transaction(function () use ($id, $version, $data) {
                $person = $this->read($id);
                // regra 2: não modificamos um registro modificado nesse meio tempo por outra pessoa
                if ($person->version !== $version) {
                    throw new BusinessException(self::MODIFIED);
                }
                if ($this->dao->namesake($data->firstName, $data->lastName, $id)) {
                    throw new BusinessException(self::NAMESAKE);
                }
                // o UPDATE "WHERE id = ... AND version = ..." não modificou nenhuma linha:
                // outra requisição modificou o registro desde que ele foi lido
                if ($this->dao->edit($id, $version, $data) === 0) {
                    throw new BusinessException(self::MODIFIED);
                }
                // o registro, lido novamente: seus novos valores e sua nova versão
                return $this->read($id);
            });
        } catch (QueryException $e) {
            throw self::translate($e);
        }
    }

    public function delete(int $id): Person
    {
        return DB::transaction(function () use ($id) {
            $person = $this->read($id);
            $this->dao->delete($id);
            return $person;
        });
    }

    // duas inclusões simultâneas: a restrição de unicidade do banco de dados recusou a
    // segunda; getMessage() contém a mensagem do MySQL, com o nome da restrição
    private static function translate(QueryException $e): Exception
    {
        if (str_contains($e->getMessage(), 'unq_persons_first_name_last_name')) {
            return new BusinessException(self::NAMESAKE, previous: $e);
        }
        return $e;
    }
}
    • linhas 17–21: as mensagens das regras de negócio;
    • linhas 32–35: uma pessoa inexistente é um erro de negócio. O operador [??] aceita uma expressão [throw] do lado direito: se a pessoa for [null], a exceção é lançada;
    • linhas 37–51: regra nº 1: duas pessoas não podem ter o mesmo nome e sobrenome. [DB::transaction] executa a função dentro de uma transação: se a função terminar normalmente, a transação é confirmada ([COMMIT]), e [DB::transaction] retorna o valor da função; se uma exceção for lançada, a transação é revertida ([ROLLBACK]): nenhuma das alterações feitas dentro da função é mantida, e a exceção prossegue. A camada de negócio determina, assim, o escopo das transações: uma operação de negócio, uma transação. A regra é verificada antes de gravar, e uma [BusinessException] é lançada se ela não for respeitada. Mas essa verificação não é suficiente: duas requisições simultâneas poderiam verificar ambas que não há duplicata e depois inserir os dados. A restrição de unicidade do banco de dados rejeita então o segundo [INSERT], e o [Laravel] dispara uma [QueryException], que o método [translate] transforma na mesma [BusinessException]. O banco de dados é a última linha de defesa;
    • linhas 53–76: regra nº 2: não modificar um registro que foi modificado nesse meio-tempo por outra pessoa. O formulário de atualização carrega a versão do registro que foi lida (em um campo oculto); se ela for diferente da versão atual, o registro mudou desde que foi exibido. Aqui também, o banco de dados (por meio do bloqueio otimista na camada DAO) detecta quando ocorre uma modificação concorrente entre a leitura e a transação [UPDATE]: a transação [UPDATE] não modifica então nenhuma linha. O registro é então lido novamente, com seus novos valores;
    • linhas 78–85: a exclusão marca a pessoa como excluída para a mensagem de confirmação;
    • linhas 89–95: [getMessage()] contém a mensagem do [MySQL], incluindo o nome da restrição violada. Qualquer outro erro é repassado como está: não é um erro de negócio, mas um erro de programação. O parâmetro chamado [previous] anexa a exceção original à nova para o log.

// app/Http/Controllers/PersonsController.php: a camada WEB; ela só conhece a camada de negócio

namespace App\Http\Controllers;

use App\Http\Requests\PersonRequest;
use App\Business\BusinessException;
use App\Business\PersonsBusiness;
use Illuminate\Http\RedirectResponse;
use Illuminate\View\View;

class PersonsController
{
    public function __construct(private PersonsBusiness $business)
    {
    }

    public function home(): RedirectResponse
    {
        return redirect()->route('persons.list');
    }

    public function list(): View
    {
        return view('persons.list', ['persons' => $this->business->list()]);
    }

    public function addForm(): View
    {
        return view('persons.form', ['title' => 'Add a person',
            'action' => route('persons.add'), 'person' => null]);
    }

    // PersonRequest: um formulário inválido não chega até aqui (veja o exemplo 19)
    public function add(PersonRequest $request): RedirectResponse
    {
        try {
            $p = $this->business->add($request->personData());
        } catch (BusinessException $e) {
            // uma regra de negócio recusa: volta ao formulário, com a entrada e a
            // mensagem, no final da página
            return back()->withInput()->with('error', $e->getMessage());
        }
        return redirect()->route('persons.list')->with('success', "$p->first_name $p->last_name has been added.");
    }

    public function editForm(int $id): View|RedirectResponse
    {
        try {
            $p = $this->business->read($id);
        } catch (BusinessException $e) {
            return redirect()->route('persons.list')->with('error', $e->getMessage());
        }
        return view('persons.form', ['title' => 'Edit a person',
            'action' => route('persons.edit', $id), 'person' => $p]);
    }

    public function edit(PersonRequest $request, int $id): RedirectResponse
    {
        try {
            $p = $this->business->edit($id, (int) $request->validated('version'), $request->personData());
        } catch (BusinessException $e) {
            return back()->withInput()->with('error', $e->getMessage());
        }
        return redirect()->route('persons.list')->with('success', "$p->first_name $p->last_name has been edited.");
    }

    public function delete(int $id): RedirectResponse
    {
        try {
            $p = $this->business->delete($id);
        } catch (BusinessException $e) {
            // nenhum formulário a exibir novamente: o erro também viaja como mensagem flash
            return redirect()->route('persons.list')->with('error', $e->getMessage());
        }
        return redirect()->route('persons.list')->with('success', "$p->first_name $p->last_name has been deleted.");
    }
}
    • linha 14: a camada de negócio, a única camada conhecida pelo controller;
    • linhas 35–45: o processo de adição, em três etapas: validação do formulário (erros de entrada), realizada antes da chamada da action pelo form request; a chamada à camada de negócio (regras de negócio); e depois o padrão PRG, com uma mensagem flash de sucesso. Uma [BusinessException] retorna ao formulário: [back()] redireciona para a página anterior (a página do formulário), [withInput()] preserva a entrada para [old] (exemplo 19) e [with('error', ...)] devolve a mensagem de erro, que o template exibirá no final da página. É exatamente o que o [Laravel] faz para um formulário inválido: os erros de entrada e os erros de lógica de negócio são tratados da mesma maneira;
    • linhas 47–56: o formulário de edição, preenchido previamente com a pessoa recuperada. Se a pessoa não existir, o usuário é redirecionado para a lista com uma mensagem de erro em pop-up;
    • linhas 58–66: a atualização, seguindo o mesmo padrão da adição;
    • linhas 68–77: a exclusão. Não há formulário a exibir novamente: qualquer erro também é transmitido em uma mensagem pop-up, [error].

    9.1.8. Os comandos SQL

    Vamos reiniciar a aplicação com a variável de ambiente [DB_LOG=true] (no [Linux] e no [macOS]: [DB_LOG=true php artisan serve]; para o [Windows]: [$env:DB_LOG="true"] antes de [php artisan serve]; ou modificando o arquivo [.env]) e, em seguida, acompanhar no console os comandos SQL de uma modificação. A exibição do formulário de modificação da pessoa nº 1:

      select * from `persons` where `persons`.`id` = ? limit 1 [1]

    Uma leitura pela chave primária, cujo valor é passado como parâmetro ([?]), sem transação: uma leitura isolada não exige uma. Salvando o registro com uma nova idade:

    1
2
3

6
      BEGIN
  select * from `persons` where `persons`.`id` = ? limit 1 [1]
  select * from `persons` where `first_name` = ? and `last_name` = ? and `id` <> ? limit 1 ["Marie","Pélissier",1]
  update `persons` set `first_name` = ?, `last_name` = ?, `age` = ?, `version` = version + 1 where `id` = ? and `version` = ? ["Marie","Pélissier",44,1,1]
  select * from `persons` where `persons`.`id` = ? limit 1 [1]
  COMMIT

    Em uma única transação, vemos: a leitura do registro principal, a busca por um homônimo, o [UPDATE] e a nova leitura. O [UPDATE] incrementa a versão ([version + 1], escrito como está graças ao [DB::raw]), e define a condição do bloqueio otimista ([and version = ?], com a versão lida, aqui 1). [Laravel] coloca os nomes de tabelas e colunas entre crases ([persons]), que é como esses nomes são escritos no [MySQL]. Agora vamos enviar o mesmo formulário uma segunda vez, ainda com a versão 1:

      BEGIN
  select * from `persons` where `persons`.`id` = ? limit 1 [1]
  ROLLBACK

    A versão lida (2) não é a mesma do formulário (1): a camada de negócio lançou uma [BusinessException], que reverteu a transação ([ROLLBACK]), e a página exibe “Este registro foi modificado nesse meio-tempo: recarregue-o.” Da mesma forma, o processo de adição de um homônimo para após a busca por homônimo, sem um [INSERT].
