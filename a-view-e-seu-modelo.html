    4. A view e seu modelo

    Até aqui, as actions geraram suas próprias respostas: texto, JSON e algumas tags HTML escritas como uma cadeia de caracteres. Em uma aplicação MVC, esse é o papel de uma view: um arquivo que descreve a página HTML, com marcadores para os dados que a action lhe transmite, o modelo da view.

    [Laravel] vem com seu próprio engine de views, o [Blade]. Uma view [Blade] é um arquivo cujo nome termina com [.blade.php], armazenado na pasta [resources/views] da aplicação. É um arquivo de texto, neste caso HTML, no qual três tipos de tags são interpretados no servidor:

    • [{{ expression }}]: o valor de uma expressão [PHP], inserido na página;
    • [@instruction]: uma diretiva: condição ([@if]), laço ([@foreach]), herança de template ([@extends], [@section]), inclusão ([@include])... Uma diretiva começa com [@], seguido de seu nome;
    • [{{-- commentaire --}}]: um comentário, que não aparece na página gerada.

    Todo o resto é copiado tal como está. As expressões são escritas em [PHP]: não há uma segunda linguagem para aprender. O [Blade] se parece, assim, com o [Razor], o engine de views do [ASP.NET Core MVC], que também mistura HTML e código e também usa o caractere [@]; ele difere do [Thymeleaf] ([Spring MVC]), cujas views são arquivos HTML válidos enriquecidos com atributos [th:]. Uma view [Blade] não é executada tal como está: no primeiro uso, o [Blade] a compila em um arquivo [PHP] padrão, armazenado em [storage/framework/views], que ele então reutiliza enquanto a view não for alterada. Veremos a aparência desse arquivo.

    <?php
// app/Http/Controllers/ViewsController.php: actions que retornam uma VIEW

namespace App\Http\Controllers;

use App\Models\PageModel;
use Illuminate\Http\Response;
use Illuminate\View\View;

class ViewsController
{
    // view: a engine Blade constrói a página a partir da view
    // resources/views/views/index.blade.php e das variáveis passadas no
    // array (aqui uma só, [model]); a página produzida é a resposta da action
    public function index(): View
    {
        $model = new PageModel(
            'My first view',
            'This page was built by Blade, on the server.',
            date('H:i:s'));
        return view('views.index', ['model' => $model]);
    }

    // a mesma view com outro modelo; ou outra view, com o código 404
    public function hello(string $name): View|Response
    {
        if ($name === 'unknown') {
            // a página, enviada com o código 404
            return response()->view('views.unknown', ['name' => $name], 404);
        }
        $model = new PageModel(
            "Hello $name",
            'This time, the title of the page comes from the URL.',
            date('H:i:s'));
        return view('views.index', ['model' => $model]);
    }
}
    • linhas 17–20: a action constrói o modelo da view. A função ***[date] do *[PHP] formata a hora atual: [H] para as horas, [i] para os minutos e [s]** para os segundos;
    • linha 21: a função [view] faz com que o [Blade] gere a página. O primeiro parâmetro é o nome da view: o caminho do arquivo, relativo à pasta [resources/views], em que as [/]s são substituídas por pontos e sem a extensão [.blade.php]: [views.index] refere-se ao arquivo [resources/views/views/index.blade.php]. O segundo parâmetro é um array associativo, em que cada chave se torna uma variável na view, neste caso uma só: [$model]. [view] retorna um objeto [View], que o [Laravel] transforma em uma resposta (do tipo [text/html]) ao gerar a página;
    • linha 29: outra view, com uma variável diferente ([$name]). [response()->view(...)] gera uma resposta a partir de uma view, com o código especificado, neste caso 404, para exibir uma página de erro personalizada. O tipo da action [View|Response] significa: ou uma [View] ou uma [Response];
    • linhas 31–35: a mesma view da action [index], mas com um modelo diferente. Esse é o benefício de separar as actions das views: uma mesma view pode ser usada por várias actions.

    • linhas 9–12: as diretivas [@php] e [@endphp] delimitam um bloco de código [PHP], executado neste ponto da página. Duas variáveis da view são criadas ali: o preço total, calculado pelo método [sum] de uma coleção (exemplo 03), que soma uma propriedade de cada elemento, e o número de produtos. O bloco [@php] deve ser reservado para esse tipo de preparação: o cálculo normalmente pertence à action;
    • linha 17: um valor [null] é exibido como uma string vazia. O operador [??] do [PHP] (exemplo 08) substitui um valor [null] por um valor padrão;
    • linhas 19–20: [{{ }}] escapa o HTML (2a); [{!! !!}], por outro lado, insere o valor tal como está, sem escapá-lo (2b). [{!! !!}] é reservado para o HTML gerado pela própria aplicação, nunca para dados digitados por usuários;
    • linhas 22–26: uma condição: [@if], [@elseif], [@else], [@endif], com uma condição [PHP] entre parênteses. Cada bloco é fechado por uma diretiva [@end...];
    • linhas 30–36: um laço [@foreach] ... [@endforeach], escrito como o laço [foreach] do [PHP]. Dentro dele, a variável especial [$loop] descreve o estado do laço: [$loop->index] (o número da iteração, começando em 0), [$loop->iteration] (começando em 1), [$loop->first], [$loop->last] (verdadeiro na primeira e na última iteração), [$loop->count] (o número de elementos). As variáveis externas ao laço ([$model->name]) continuam acessíveis;
    • linha 32: o operador ternário do [PHP], [condition ? a : b] (exemplo 11);
    • linha 40: a diretiva [@forelse] ... [@empty] ... [@endforelse] é um laço em que o bloco [@empty] é executado se a lista estiver vazia. Isso é mais simples do que um [@if] que testasse o tamanho da lista;
    • linhas 43–44: expressões calculadas ([$total / $count]) e as variáveis do bloco [@php]. A função [number_format] do [PHP] formata um número: duas casas decimais, um ponto como separador decimal e uma vírgula como separador de milhares. No exemplo 16, veremos uma forma muito melhor de formatar números e valores monetários;
    • linha 46: o operador [->] percorre os objetos ([$model->address->city]), e qualquer função do [PHP] pode ser chamada: [mb_strtoupper] converte uma string em maiúsculas (as funções [mb_...], de *multi-byte*, tratam corretamente os caracteres acentuados codificados em UTF-8);
    • linha 48: o caractere [@] só é interpretado pelo [Blade] no início de uma palavra; em um endereço de e-mail, ele é copiado tal como está. Para escrever um [@] seguido do nome de uma diretiva, ele é duplicado: [@@if] produz [@if]. Da mesma forma, [@{{ ... }}] produz [{{ ... }}], o que é útil quando uma página contém chaves destinadas a um framework [JavaScript].

    Uma observação sobre comentários: [Blade] processa [@php] os blocos antes dos comentários. Um comentário que contenha a palavra [@php] seria, portanto, interpretado como o início de um bloco de código, com resultados inesperados: é por isso que o comentário da linha 8 não a inclui.

namespace App\Helpers;

use Brick\Math\BigDecimal;
use Carbon\CarbonInterface;
use Illuminate\Support\Facades\App;
use Illuminate\Support\Number;

class Formats
{
    // "keyboard" -> "KEYBOARD"
    public static function uppercase(?string $text): string
    {
        return $text === null ? '' : mb_strtoupper($text);
    }

    // um valor em uma moeda, no formato do idioma da requisição (veja o middleware
    // SetLanguage): 1149.9 -> "€1,149.90" em inglês, "1 149,90 €" em
    // francês. A extensão intl do PHP conhece as convenções de cada país
    public static function money(BigDecimal $amount, string $currency = 'EUR'): string
    {
        return Number::currency($amount->toFloat(), in: $currency, locale: App::getLocale());
    }

    // uma data por extenso, no idioma da requisição: "Saturday 26 September 2026"
    public static function longDate(CarbonInterface $day): string
    {
        return $day->locale(App::getLocale())->isoFormat('dddd D MMMM YYYY');
    }
}
    • Linhas 14–17: um método estático ([static]): ele é chamado na classe, sem um objeto ([Formats::uppercase('keyboard')]). Ele aceita [null];

A classe [Number] do [Laravel] baseia-se na extensão [intl] do [PHP], que suporta as convenções de todos os países (ela usa dados do projeto Unicode *CLDR*): [Number::currency] formata um valor monetário, com a moeda designada por seu código internacional ([EUR], [USD]).     4.5. Exemplo 17: um formulário GET

    Um formulário HTML envia seus campos ao servidor de uma de duas maneiras, dependendo de seu atributo [method]:

namespace App\Http\Controllers;

use App\Models\Book;
use App\Models\SearchModel;
use Illuminate\Http\Request;
use Illuminate\View\View;

class BooksController
{
    // CONSTANTES de classe: os dados, escritos no código para o exemplo
    private const GENRES = ['novel', 'poetry', 'drama'];

    /** @return list<Book> */
    private static function books(): array
    {
        return [
            new Book('Le Rouge et le Noir', 'Stendhal', 'novel'),
            new Book('Les Fleurs du mal', 'Baudelaire', 'poetry'),
            new Book('Madame Bovary', 'Flaubert', 'novel'),
            new Book('Alcools', 'Apollinaire', 'poetry'),
            new Book('Le Cid', 'Corneille', 'drama'),
        ];
    }

    // GET / e GET /search?keyword=...&genre=...: o formulário E seus resultados
    public function search(Request $request): View
    {
        // string: o parâmetro, na forma de uma string ('' se estiver ausente)
        $keyword = $request->string('keyword')->value();
        $genre = $request->string('genre')->value();
        $word = mb_strtolower($keyword);
        $results = array_values(array_filter(self::books(), fn (Book $book) =>
            ($word === '' || str_contains(mb_strtolower($book->title), $word)
                || str_contains(mb_strtolower($book->author), $word))
            && ($genre === '' || $book->genre === $genre)));
        return view('books.search', [
            'model' => new SearchModel($keyword, $genre, self::GENRES, $results),
        ]);
    }
}

    public function process(Request $request): View
    {
        $l = $this->lists;
        // array_keys: os VALORES permitidos de cada lista (as chaves dos arrays)
        $validator = Validator::make($request->post(), [
            'title' => ['required', Rule::in(array_keys($l->titles()))],
            'birth_date' => 'nullable|date_format:Y-m-d',
            'hobbies' => 'array',
            'hobbies.*' => Rule::in(array_keys($l->hobbies())),
            'country' => ['required', Rule::in(array_keys($l->countries()))],
            'languages' => 'array',
            'languages.*' => Rule::in(array_keys($l->languages())),
        ]);
        // o que o navegador realmente enviou, parâmetro por parâmetro
        $received = [];
        foreach ($request->post() as $name => $value) {
            $received[] = "$name = [".implode(', ', (array) $value).']';
        }
        return view('form.form', [
            'lists' => $l,
            'input' => $request->post(),
            'received' => implode("\n", $received),
            'valid' => $validator->passes(),
            'errors' => $validator->errors(),
        ]);
    }

    4.8. Exemplo 20: o padrão Post/Redirect/Get

    Quando uma ação POST retorna uma página, essa página é o resultado de um POST. Se o usuário atualiza a página (pressionando [F5]), o navegador reenvia a requisição POST, após um aviso que poucas pessoas leem: o comando é enviado duas vezes, e a mensagem é publicada duas vezes. O padrão Post/Redirect/Get (PRG) evita esse problema: uma ação POST bem-sucedida não retorna uma página; ela responde com um redirecionamento (exemplo 04) para uma página GET, que o navegador solicita imediatamente. Recarregar essa página simplesmente executa de novo a ação GET.

    Resta um problema: a página GET gostaria de exibir uma mensagem (“a tarefa foi adicionada”), mas é a ação POST que conhece essa mensagem, e ela não pode passar uma variável para uma requisição que ainda não ocorreu. A solução: a mensagem flash, armazenada na sessão pela ação POST, é mantida até a próxima requisição, exibida e depois descartada. É o mecanismo que o [Laravel] já usava, no exemplo 19, para os erros de formulário.

// app/Services/TasksService.php: a lista de tarefas, compartilhada por todos os
// usuários. Em PHP, os objetos não sobrevivem à requisição: a lista é

namespace App\Services;

use Illuminate\Support\Facades\Cache;

class TasksService
{
    private const KEY = 'tasks';

    /** @return list<string> */
    public function list(): array
    {
        // o valor armazenado sob a chave [tasks], ou a lista inicial
        return Cache::get(self::KEY, ['Read chapter 3']);
    }

    public function add(string $label): void
    {
        // várias requisições podem ser executadas AO MESMO TEMPO (o servidor as trata
        // em vários processos): um lock garante que apenas uma por vez
        // leia, modifique e regrave a lista. block(5, ...) espera pelo lock no máximo 5
        // segundos, executa a função e depois libera o lock
        Cache::lock('tasks-lock', 10)->block(5, function () use ($label) {
            $tasks = $this->list();
            $tasks[] = $label;
            // forever: o valor é mantido sem limite de tempo
            Cache::forever(self::KEY, $tasks);
        });
    }

    A lista de tarefas é compartilhada por todos os usuários e deve persistir de uma requisição para a seguinte. Em [Java], [C#] ou [Python], ela seria mantida em memória dentro de um único serviço. Em [PHP], isso é impossível: como vimos nos exemplos 01 e 06, nada sobrevive à requisição. A lista deve, portanto, ser armazenada fora do [PHP]: em um banco de dados, em um arquivo... ou no cache do [Laravel], que usamos aqui.

    • Linha 18: a interface [Cache] dá acesso ao cache da aplicação: um armazenamento de pares chave→valor. O arquivo [.env] dos exemplos armazena esses dados em arquivos dentro da pasta [storage/framework/cache] ([CACHE_STORE=file], exemplo 01); em produção, prefere-se um servidor dedicado, como o [Redis]. Qualquer valor (neste caso, um array de strings) pode ser armazenado: o [Laravel] o serializa — isto é, converte-o em texto — usando a função [serialize] do [PHP];
    • Linhas 27–32: o servidor de desenvolvimento, como um servidor de produção, pode processar várias requisições ao mesmo tempo, em vários processos (a variável de ambiente [PHP_CLI_SERVER_WORKERS] define o número de processos de [php artisan serve]). Um lock garante que apenas uma requisição por vez execute o código que ele protege: [Cache::lock('tasks-lock', 10)] cria um lock nomeado — que também é armazenado no cache — que expira após no máximo 10 segundos (caso a requisição que o detém seja encerrada abruptamente); [block(5, function)] espera até 5 segundos para que o lock fique disponível, adquire-o, executa a função e depois o libera. A palavra-chave [use] em uma função anônima dá a ela acesso a uma variável da função que a contém (aqui, [$label]); uma função de seta, por outro lado, enxerga essas variáveis automaticamente;

use App\Models\Contact;
use Illuminate\Support\Facades\Cache;

class ContactsService
{
    private const KEY = 'contacts';

    /** @return array{contacts: list<Contact>, lastId: int} */
    private function data(): array
    {
        return Cache::get(self::KEY, [
            'contacts' => [
                new Contact(1, 'Marie Durand', '01 23 45 67 89'),
                new Contact(2, 'Paul Martin', '06 12 34 56 78'),
                new Contact(3, 'Philippe Jandot', '02 98 76 54 32'),
            ],
            'lastId' => 3,
        ]);
    }

    // uma modificação dos dados, sob lock: a função recebe os dados,
    // os modifica (&) e retorna o resultado da operação
    private function editData(callable $operation): mixed
    {
        return Cache::lock('contacts-lock', 10)->block(5, function () use ($operation) {
            $data = $this->data();
            $result = $operation($data);
            Cache::forever(self::KEY, $data);
            return $result;
        });
    }

    /** @return list<Contact> */
    public function list(): array
    {
        return $this->data()['contacts'];
    }

    // o contato, ou null se ele não existir
    public function read(int $id): ?Contact
    {
        return array_find($this->list(), fn (Contact $c) => $c->id === $id);
    }

    public function edit(int $id, string $name, string $phone): ?Contact
    {
        return $this->editData(function (array &$data) use ($id, $name, $phone) {
            foreach ($data['contacts'] as $i => $contact) {
                if ($contact->id === $id) {
                    // um contato é imutável (readonly): construímos um novo,
                    // que substitui o antigo no array
                    return $data['contacts'][$i] = new Contact($id, $name, $phone);
                }
            }
            return null;
        });
    }

    public function add(string $name, string $phone): Contact
    {
        return $this->editData(function (array &$data) use ($name, $phone) {
            $contact = new Contact(++$data['lastId'], $name, $phone);
            $data['contacts'][] = $contact;
            return $contact;
        });
    }

    public function delete(int $id): ?Contact
    {
        return $this->editData(function (array &$data) use ($id) {
            foreach ($data['contacts'] as $i => $contact) {
                if ($contact->id === $id) {
                    // array_splice remove o item i do array e renumera os seguintes
                    array_splice($data['contacts'], $i, 1);
                    return $contact;
                }
            }
            return null;
        });
    }
}

    Os contatos são armazenados no cache, assim como as tarefas do exemplo 20. Cada contato é um objeto [Contact] imutável (um ID, um nome, um telefone), armazenado em um array junto com o último ID atribuído. Alguns pontos sobre o [PHP]:

    • Linhas 29–37: todas as modificações seguem o mesmo padrão: adquirir o lock, ler os dados, modificá-los, gravá-los de volta e liberar o lock. Este método grava no array uma única vez; cada modificação passa a ele uma função (do tipo [callable], “chamável”), que recebe os dados e os modifica. A função deve modificar o próprio array, e não uma cópia: seu parâmetro é declarado como [array &$data], em que [&] especifica uma passagem por referência (sem [&], um array é copiado; veja o exemplo 06);
    • linhas 51–63: um contato é imutável: cria-se um novo, que substitui o antigo no array. Uma atribuição é uma expressão cujo valor é o valor atribuído: [return $data['contacts'][$i] = new Contact(...)] substitui o contato e o retorna;
    • linha 68: [++] colocado antes de uma variável a incrementa em 1 e retorna o novo valor;
    • linha 80: [array_splice] remove um elemento do array e renumera os elementos seguintes;
    • Os métodos retornam [null] para um contato inexistente: cabe ao controller decidir a resposta.

// app/Http/Controllers/ContactsController.php: links (GET) e botões (POST, DELETE)

namespace App\Http\Controllers;

use App\Models\Contact;
use App\Services\ContactsService;
use Illuminate\Http\RedirectResponse;
use Illuminate\Http\Request;
use Illuminate\View\View;

class ContactsController
{
    public function __construct(private ContactsService $contacts)
    {
    }

    // o contato, ou uma resposta 404 se ele não existir
    private static function contactOr404(?Contact $contact): Contact
    {
        abort_if($contact === null, 404, 'unknown contact');
        return $contact;
    }

    // um LINK (<a href>): uma requisição GET, que não modifica nada
    public function list(): View
    {
        return view('contacts.list', ['contacts' => $this->contacts->list()]);
    }

    public function details(int $id): View
    {
        return view('contacts.details', ['contact' => self::contactOr404($this->contacts->read($id))]);
    }

    // um BOTÃO em um formulário POST: uma requisição que modifica dados
    public function save(Request $request, int $id): RedirectResponse
    {
        $contact = self::contactOr404($this->contacts->edit($id,
            $request->string('name')->value(), $request->string('phone')->value()));
        return redirect()->route('contacts')->with('message', "The contact [$contact->name] has been edited.");
    }

    // mesmo formulário, outro botão (atributo formaction): outra action
    public function duplicate(Request $request, int $id): RedirectResponse
    {
        $copy = $this->contacts->add($request->string('name')->value().' (copy)',
            $request->string('phone')->value());
        return redirect()->route('contacts')->with('message', "The contact [$copy->name] has been created.");
    }

    // uma requisição DELETE, simulada por um formulário POST (veja @method na view)
    public function delete(int $id): RedirectResponse
    {
        $contact = self::contactOr404($this->contacts->delete($id));
        return redirect()->route('contacts')->with('message', "The contact [$contact->name] has been deleted.");
    }
}

    • linhas 37–42: salvar a ficha: uma ação POST, que segue o esquema PRG. A mesma URL, [/contacts/2], é tratada por duas ações diferentes, dependendo do método: GET exibe, POST salva;
    • Linhas 45–50: duplicação — outra ação POST, disparada por um segundo botão do mesmo formulário;
    • Linhas 53–57: a exclusão, tratada por uma requisição DELETE.

    // confirmação dos formulários que carregam o atributo data-confirmation="..."
// Sem JavaScript, esses formulários são simplesmente enviados sem confirmação.
(() => {
  const modal = document.getElementById('confirmation-modal');
  const message = document.getElementById('confirmation-modal-message');
  let pending = null; // o formulário a enviar se o usuário confirmar

  // 1. interceptamos o envio dos formulários a confirmar
  document.querySelectorAll('form[data-confirmation]').forEach((form) => {
    form.addEventListener('submit', (event) => {
      event.preventDefault(); // o envio é suspenso
      pending = form;
      message.textContent = form.dataset.confirmation;
      modal.classList.remove('d-none'); // a janela aparece
    });
  });

  // 2. os dois botões da janela
  modal.addEventListener('click', (event) => {
    const action = event.target.dataset.action;
    if (action === 'yes') {
      pending.submit(); // envio, SEM disparar novamente o evento 'submit'
    } else if (action === 'no') {
      modal.classList.add('d-none');
      pending = null;
    }
  });
})();
    • linha 3: o código é envolvido em uma função anônima, que é executada imediatamente; suas variáveis não interferem nas dos outros scripts da página;
    • linhas 4–6: a janela, o local da mensagem e o formulário que aguarda confirmação;
    • linhas 9–14: para cada formulário que tenha um atributo [data-confirmation], o evento [submit] — disparado quando o formulário é enviado — é interceptado. [preventDefault()] suspende o envio; o formulário fica em espera, e sua mensagem ([dataset.confirmation], o valor do atributo [data-confirmation]) é exibida na janela, que aparece;
    • linhas 19–25: um único handler para os cliques na janela: [event.target] é o elemento clicado; seu atributo [data-action] especifica de qual botão se trata. “Yes” envia o formulário pendente com o método [submit()], que — ao contrário de clicar em um botão — não dispara o evento [submit] (caso contrário, a janela reapareceria); “No” oculta a janela.

    Sem [JavaScript], o formulário é simplesmente enviado sem confirmação: a página continua utilizável. Isso é aprimoramento progressivo: [JavaScript] acrescenta comodidade, mas a aplicação não depende dele.
