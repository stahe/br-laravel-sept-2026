    5. Internacionalização

    Uma aplicação internacionalizada exibe seu texto no idioma do usuário. O estudo de caso está em francês e inglês. O princípio é simples: as views não contêm mais texto, mas chaves ([MENU.HOME]), e um dicionário para cada idioma associa um texto a cada chave. O idioma selecionado é armazenado em um cookie.

    [Laravel] tem seu próprio sistema de tradução, que já encontramos no exemplo 09 para as mensagens de validação. Ele aceita dois tipos de dicionários, armazenados na pasta [lang]: arquivos [PHP], um por tema e por idioma ([lang/fr/validation.php]), que retornam um array de chaves; e arquivos JSON, um por idioma ([lang/fr.json]), em que cada chave é uma string arbitrária. Usamos o segundo formato: exceto pela sintaxe dos parâmetros, são os mesmos dicionários das versões [ASP.NET Core MVC], [NestJS], [Spring MVC] e [Flask] do estudo de caso, e seu formato pode ser lido e escrito sem nenhuma ferramenta especial. A formatação de datas e valores monetários permanece a mesma do exemplo 16.

Um texto pode conter placeholders, escritos como [:name], que são substituídos durante a tradução. (Os dicionários das outras versões do estudo de caso aninham os objetos JSON — [{"MENU": {"HOME": "Accueil"}}] — e escrevem os parâmetros como [{name}]; os do [Laravel] são “planos” e usam a sintaxe [:name].) Não há dicionário (JSON) de reserva: uma chave ausente do dicionário (JSON) do idioma atual e desses arquivos é exibida tal como está. Assim, qualquer omissão fica imediatamente visível na tela.

    <?php
// app/Http/Middleware/SetLanguage.php: o idioma de cada requisição

namespace App\Http\Middleware;

use Closure;
use Illuminate\Http\Request;
use Illuminate\Support\Facades\App;
use Symfony\Component\HttpFoundation\Response;

class SetLanguage
{
    // os idiomas suportados; o primeiro é o idioma padrão
    public const LANGUAGES = ['en', 'fr'];

    public const COOKIE = 'language';

    // o idioma do cookie [language] se for suportado, inglês caso contrário
    public function handle(Request $request, Closure $next): Response
    {
        $language = $request->cookie(self::COOKIE);
        App::setLocale(in_array($language, self::LANGUAGES, true) ? $language : self::LANGUAGES[0]);
        return $next($request);
    }
}
    • linhas 14–16: os idiomas suportados e o nome do cookie: constantes de classe públicas, acessíveis de outras classes ([SetLanguage::LANGUAGES]);
    • linhas 21–22: antes de cada ação, o idioma da requisição: o idioma especificado no cookie [language] se ele existir e for suportado; caso contrário, inglês. [$request->cookie(name)] retorna o valor de um cookie enviado pelo navegador, ou [null]. [in_array], com [true] como terceiro parâmetro, também compara os tipos ([===]). [App::setLocale] (exemplo 16) define o idioma da aplicação para a requisição: é o idioma usado para as traduções e a formatação.

use App\Http\Middleware\SetLanguage;

(require __DIR__.'/../../vendor/autoload.php')->addPsr4('App\\', __DIR__.'/../app/');

    ->withRouting(
        web: __DIR__.'/../routes/web.php',
        // a rota que serve o Bootstrap (veja o exemplo 15)
        then: fn () => require __DIR__.'/../../common/bootstrap.php')
    ->withMiddleware(function (Middleware $middleware): void {
        // o cookie [language] não é criptografado: ele não contém nada secreto, e
        // o servidor aceita apenas os idiomas suportados
        $middleware->encryptCookies(except: [SetLanguage::COOKIE]);
        // o idioma de cada requisição: o do cookie [language], inglês caso contrário
        $middleware->web(append: SetLanguage::class);
    })
    ->withExceptions()
    ->booted(function () {
        // nas views: @money($price) (veja o exemplo 16)
        Blade::directive('money', fn (string $expression) =>
            "<?php echo e(\\App\\Helpers\\Formats::money($expression)); ?>");
    })
    ->create();
    • Linha 19: por padrão, o [Laravel] criptografa todos os cookies que define e descriptografa os que recebe (esse é o papel do middleware [EncryptCookies] do grupo [web]; veja o exemplo 20): o usuário não pode ler nem criar um cookie criptografado. O cookie [language] não contém nenhuma informação secreta, e o servidor aceita apenas idiomas suportados: nós o excluímos da criptografia, o que nos permite visualizá-lo (e criá-lo) usando o [curl]. O exemplo seguinte voltará a essa criptografia;
    • linha 21: o middleware de idioma, no final do grupo [web] (exemplo 16): ele é executado depois de [EncryptCookies] e, portanto, lê cookies que já foram descriptografados;
    • linhas 26–27: a diretiva [@money] do exemplo 16.

    <?php
// app/Helpers/Formats.php: datas e valores, formatados no idioma da requisição (veja o exemplo 16)

namespace App\Helpers;

use Brick\Math\BigDecimal;
use Carbon\CarbonInterface;
use Illuminate\Support\Facades\App;
use Illuminate\Support\Number;

class Formats
{
    // um valor em euros
    public static function money(BigDecimal $amount): string
    {
        return Number::currency($amount->toFloat(), in: 'EUR', locale: App::getLocale());
    }

    // uma data por extenso. O formato "dddd LL": o dia da semana, depois a
    // data no formato "longo" do idioma: "mercredi 23 septembre 2026" em francês,
    // "Wednesday September 23, 2026" em inglês
    public static function longDate(CarbonInterface $day): string
    {
        return $day->locale(App::getLocale())->isoFormat('dddd LL');
    }
}
    • Linha 24: [LL] é um formato localizado: cada idioma tem o seu ([23 septembre 2026] em francês, [September 23, 2026] em inglês), ao passo que [D MMMM YYYY] imporia a ordem francesa a todos os idiomas. [dddd] acrescenta o dia da semana.

    <?php
// app/Http/Controllers/LanguageController.php: a escolha do idioma

namespace App\Http\Controllers;

use App\Http\Middleware\SetLanguage;
use Illuminate\Http\RedirectResponse;
use Illuminate\Http\Request;

class LanguageController
{
    // GET /language/fr: armazena a escolha em um cookie e depois volta à página anterior
    public function change(Request $request, string $code): RedirectResponse
    {
        abort_unless(in_array($code, SetLanguage::LANGUAGES, true), 404);
        // o cookie: um ano de vida (em minutos), ilegível pelo JavaScript da
        // página (httpOnly), nunca enviado com uma requisição POST vinda de outro site (sameSite)
        return redirect(self::originPage($request))
            ->withCookie(cookie(SetLanguage::COOKIE, $code, 365 * 24 * 60, httpOnly: true, sameSite: 'lax'));
    }

    // a página de onde viemos (cabeçalho Referer), da qual mantemos apenas o caminho:
    // redirecionar para um endereço completo vindo da requisição permitiria
    // enviar o usuário a outro site (falha de "open redirect")
    private static function originPage(Request $request): string
    {
        // parse_url divide uma URL em seus componentes (caminho, parâmetros...)
        $url = parse_url($request->header('Referer', ''));
        $path = $url['path'] ?? '';
        // "//site.com/..." seria entendido pelo navegador como um endereço
        // em OUTRO site: também recusado
        if (! str_starts_with($path, '/') || str_starts_with($path, '//')) {
            return '/';
        }
        return isset($url['query']) ? "$path?{$url['query']}" : $path;
    }
}
    • linha 15: um código de idioma desconhecido: 404;
    • linhas 18–19: a ação responde com um redirecionamento para a página de onde o usuário veio; o usuário é levado de volta a essa página no novo idioma. A resposta inclui um cookie, que o navegador devolverá a cada requisição: a função [cookie] o cria, e o método [withCookie] o adiciona à resposta. Seus parâmetros: o nome, o valor, a duração em minutos (um ano) e dois parâmetros nomeados: [httpOnly: true] o torna invisível para o [JavaScript] da página; [sameSite: 'lax'] impede que o navegador o envie com uma requisição POST originada de outro site;
    • linhas 25–36: a página de origem é especificada pelo cabeçalho [Referer] da requisição (a grafia incorreta, com um único [r], é a usada no padrão HTTP), que o navegador preenche com a URL da página que continha o link. Mas esse cabeçalho vem do cliente, que pode colocar qualquer coisa nele. Redirecionar cegamente para esse endereço transformaria nossa aplicação em um *open redirect*: um link malicioso com o nome do nosso domínio poderia enviar o usuário a um site malicioso. Por isso, mantemos apenas o caminho e os parâmetros da URL (a função [parse_url] do [PHP] a decompõe em seus componentes, armazenando-os em um array associativo) e rejeitamos qualquer caminho que comece com [//], que o navegador interpretaria como o endereço de outro site. [Laravel] também fornece [redirect()->back()] (ou [back()]), que redireciona para a página anterior armazenada na sessão (exemplo 20), e não para o cabeçalho [Referer]: usaremos isso no estudo de caso.
